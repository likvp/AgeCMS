# Модуль importer: перенос сайта с другой CMS

Переносит содержимое существующего сайта в страницы AgeCMS: тексты, картинки, структуру страниц, меню, SEO-поля и старые адреса (постоянные переходы 301). В режиме «В блоки темы» дизайн не переносится: страницы собираются из блоков активной темы. Режим «Точная копия» сохраняет вид источника (см. ниже).

Источники:

| Источник | Как читается |
| --- | --- |
| WordPress по адресу | открытый REST API `/wp-json/wp/v2/` (или `?rest_route=`): страницы, записи, SEO Yoast / Rank Math / AIOSEO, картинки записей. Страницы Elementor, Divi, WPBakery берутся с готового сайта. Если API закрыт, сайт обходится как обычный |
| WordPress, файл выгрузки (WXR) | «Инструменты», «Экспорт», «Всё содержимое»: страницы, записи, вложения, многоразовые блоки, меню (`nav_menu_item`), поля Yoast в postmeta |
| Tilda по адресу | записи страницы (`.t-rec`): обложки, заголовки и тексты, картинки, кнопки, FAQ (T585, T668 и похожие), формы, галереи. Zero Block (T396) переносится по порядку сверху вниз с пометкой «перенесите вручную»; Zero Block в шапке из логотипа и ссылок становится меню, лента логотипов галереей. Посты Потоков (`/tpost/`, карта `sitemap-feeds.xml`) становятся записями блога с датой, им отдаётся треть лимита страниц. Магазин (`sitemap-store.xml`, `/tproduct/`) не переносится, с пометкой. Общий подвал (контакты, реквизиты) в страницы не идёт: пометка на главной, страница без своих блоков получает подвал как содержимое. Копии одной страницы (`/`, `/glavnaya`, `/page123.html`) дают одну страницу и 301 с остальных адресов |
| Tilda, архив экспорта (.zip) | страницы `page*.html` (и добавленные вручную `*.html`), адреса из `htaccess`, картинки из папки `images/` с диска. Оболочка, которая подгружает `files/page*body.html` скриптом, берёт записи из этого файла; страница общего подвала или шапки не переносится |
| 1С-Битрикс | рабочая область шаблона, хлебные крошки (иерархия), новости `/news/`, `/about/news/` как записи с датой; кодировка windows-1251 |
| OpenCart | только информационные страницы (о магазине, доставка, оплата, контакты, политика) и новости: товары, категории, производители и поиск пропускаются; после 30 подряд страниц каталога просмотр останавливается. Страницы первого уровня со ссылкой с главной идут раньше карты сайта (в ней каталог стоит первым) |
| Wix | текст и картинки, которые Wix отдаёт сервером. Сайт в папке (`user.wixsite.com/site`) переносится в корень: `/site/about` становится `/about`, со старого адреса 301. Галереи (Pro Gallery) и запись (Bookings) Wix рисует скриптом: без JS эти страницы пустые, переносить нечего |
| Joomla, MODX, HostCMS, Webflow, Drupal, UMI и любой другой сайт | sitemap.xml (вложенные индексы, строки `Sitemap:` в robots.txt), иначе обход ссылок с главной; основное содержимое по контейнерам CMS или по плотности текста. У WordPress без REST сначала карты страниц и записей, потом других типов записей; карты рубрик, меток и авторов не читаются |

## Как запустить

**Админка**: «Импорт сайта» (`/admin/m/importer/`, только администратор). Адрес сайта или файл выгрузки, лимит страниц, что делать с занятыми адресами. Файл (.xml WordPress или .zip Tilda) загружается прямо в форме: ядро проверяет сигнатуру и размер (до 50 МБ, но не больше `upload_max_filesize` и `post_max_size` сервера, предел показан у поля), файл хранится только под `data/`. Больший файл кладётся по FTP в папку `data/import/` сайта и выбирается в списке. Затем предпросмотр: платформа и признаки, страницы со старыми и новыми адресами, блоки и потери каждой страницы, галочки. Кнопка «Импортировать», прогресс, отчёт, «Отменить импорт». Страница задания (`/admin/m/importer/job?id=N`) показывает прогресс без перезагрузки: скрипт админки ядра (`data-ag-step`) отправляет шаг за шагом и каждый шаг делает следующую порцию работы. Без JavaScript страница обновляется сама и тоже делает шаг при каждом обновлении.

**Командная строка** (из корня сайта):

```bash
php modules/importer/bin/import.php https://old-site.ru               # предпросмотр: дерево, блоки, потери, редиректы
php modules/importer/bin/import.php https://old-site.ru --json --full # то же в JSON, с исходными страницами и блоками
php modules/importer/bin/import.php export.xml --apply                # перенос
php modules/importer/bin/import.php --status=3
php modules/importer/bin/import.php --rollback=3
```

Параметры: `--limit=N`, `--delay=мс`, `--no-robots`, `--conflict=skip`, `--replace-home`, `--no-menus`, `--section=blog`, `--pages=/a,/b` (с `--apply`), `--quiet`. Предпросмотр работает и на неустановленной копии (без проверки занятых адресов), перенос только на установленном сайте.

`--allow-private` (только командная строка, для проверки импорта): разрешает источник на этой машине или в локальной сети и любой порт, например WordPress в Docker на `http://127.0.0.1:8090`. Защита от запросов во внутреннюю сеть на это время снимается для всего процесса, в админке и навыках такого параметра нет.

**Навыки агента** (только администратор): `importer__import_detect` (url), `importer__import_preview` (url или file_base64 с type `wxr` / `tilda_zip`, limit, conflict, replace_home, menus, section), `importer__import_apply` (job_id, pages: список old_path или id), `importer__import_status` (job_id; каждый вызов делает следующую порцию), `importer__import_rollback` (job_id). Агент отменяет импорт любого размера, если перенос запускал этот же токен; импорт человека или другого токена агенту доступен для отмены только до двух страниц, больший отменяет владелец в админке.

**Настройки модуля** («Система», «Настройки» у модуля): страниц за импорт (200), пауза между запросами (500 мс), страниц за шаг (5), соблюдать robots.txt.

## Как устроено

1. **Анализ.** Сборщик (`src/Extract/`) читает источник и отдаёт страницы в нейтральном формате (ниже). Распознавание платформы (`src/Detect/Detector.php`) по meta generator, адресам (`/wp-content/`, `/bitrix/`, `tildacdn`, `/media/jui/`, `wixstatic`...), атрибутам (`data-tilda-page-id`, `data-wf-page`), заголовкам и cookie; уверенность от 0 до 1 и список признаков.
2. **План** (`src/Planner.php`, `src/Mapper.php`). Новые адреса, родители, разделы блога, конфликты, редиректы, меню; элементы раскладываются в блоки темы. На сайте ничего не меняется.
3. **Перенос** (`src/Runner.php`) порциями по несколько страниц: картинки в медиатеку (одна картинка один файл, адрес не скачивается дважды), страницы через `Content` от имени того, кто запустил импорт (видно в истории), затем редиректы и меню. Каждый шаг укладывается в 20 секунд и продолжается следующим запросом, вызовом навыка или фоновым тиком (`background.tick`).
4. **Отмена.** Созданные страницы уходят в корзину (страница, изменённая после импорта, остаётся), редиректы удаляются, меню возвращается, если его не меняли. Главная, заменённая импортом, получает прежнее содержимое. Страницы удаляются явной отменой сессии задания `imp-<номер>` (`CircuitBreaker::allowRollback`, `Content::rollbackSession`): удаление не считается в 15% предохранителя, поэтому большой импорт отменяется и через сутки, и через неделю. Разрешение пишется в историю. Сессию задания при переносе закрепляет за собой тот, кто его запустил (`claimSession`), поэтому агент может отменить только импорт своего токена.

Сетевые запросы идут через защиту ядра от запросов во внутреннюю сеть (`Http::guard`, адрес закрепляется за проверенным IP на каждом переходе), с User-Agent `AgeCMS-Importer/1.0 (+адрес сайта)`. Страница ждётся до 15 секунд, карта сайта до 90 секунд (большая карта магазина генерируется долго) и обрывается раньше, только если передача встала (меньше 100 байт в секунду 30 секунд). robots.txt проверяется и для REST API WordPress, ещё при распознавании. Таблицы `mod_importer_jobs`, `mod_importer_items`, `mod_importer_media` создаются при первом импорте: на сайте, где импорт не запускали, модуль ничего не пишет ни в базу, ни в историю.

## Нейтральный формат

Все сборщики отдают одно и то же, остальная часть модуля не знает, откуда пришла страница.

```text
Site {
  source_url, platform, title,
  pages[]: Page,
  menus: {header: [{title, url}], footer: [{title, url}]},
  assets[]
}

Page {
  source_url        адрес, с которого взята страница
  old_path          путь со старого сайта; с запросом, если адрес вида /?p=12, /index.php?id=3
  aliases[]         другие старые адреса той же страницы (/?page_id=7, /page123.html, guid)
  suggested_slug    адрес, который предлагает CMS (post_name WordPress)
  parent_old_path   старый путь родителя (из WordPress или хлебных крошек)
  kind              page | post
  title, meta_title, meta_description, canonical, og_image
  published_at      дата записи, YYYY-MM-DD
  is_noindex
  elements[]: Element
  notes[]           что не перенесётся: {what, why, source}
  skip              необязательно: причина не переносить страницу (товар магазина, пустая служебная страница)
  tilda_page_id     необязательно: номер страницы Tilda, по нему находятся копии одной страницы
}
```

Элементы (`type` и поля; у каждого есть `source`: откуда взят, для отчёта):

| type | поля |
| --- | --- |
| heading | level (1-6), text |
| paragraph | html (строчная разметка: strong, em, u, s, a, br, code) |
| list | ordered, items (html пунктов) |
| image | src, alt, caption; width, height, если их указывает разметка |
| gallery | images: [{src, alt, caption}] |
| quote | html, cite |
| table | html |
| button | text, url |
| hero | h1, subtitle, cta_text, cta_url, image |
| faq | items: [{q, a}] (a: html) |
| form | fields: [{name, label, type}], submit_text |
| embed | src, kind: video, map или other |
| raw | html, note: почему не разобрано |

Картинка из архива экспорта записывается как `local:путь/в/архиве`, при переносе она берётся с диска. Элемент может нести `anchor` (список имён якорей источника, например `<a name="service">` Tilda; запись Tilda ещё и свой `rec123` по полю `source`): пункт меню `/#service` ведёт на блок, в который попал этот элемент.

## Раскладка по блокам темы

Схема берётся из `theme.json` активной темы. Каждый тип блока получает роль:

| Роль | Что туда идёт | Как узнаётся без подсказки |
| --- | --- | --- |
| hero | первый экран: обложка или h1 страницы, подзаголовок, кнопка | поле `h1` или имя hero/cover/banner |
| article | подряд идущие заголовки, абзацы, списки, цитаты, таблицы, картинки рядом с текстом и галереи | поле типа `richtext` |
| text | то же простым текстом, если в теме нет richtext | обязательное поле `text`, нет списков |
| faq | вопросы и ответы | поле-список с `q`/`question` |
| image | крупная картинка, стоящая отдельно (без текста рядом); галерея, если в теме нет richtext | обязательное поле `url` с `media` |
| form | форма (ставится форма заявки сайта) | имя с form/lead/contact или поля button_text и success_text |
| list | список карточек | поле-список |
| child_pages | список записей раздела блога | имя child_pages или поле `parent` |

Тема может указать роль явно новым необязательным полем блока `import`, оно важнее догадок:

```json
"promo": {"title": "Первый экран", "import": "hero", "fields": {"title": {"type": "string", "required": true}, "lead": {"type": "text"}}}
```

Значения: `hero`, `article`, `text`, `faq`, `image`, `form`, `list`, `child_pages`. Ядро это поле не читает, оно только для импорта.

Правила: обложка (или первый h1, или заголовок, повторяющий название страницы) становится первым экраном; если в hero темы нет картинки, картинка обложки идёт отдельным блоком. Картинка с текстом рядом и галерея идут в статью (`<figure>` одна за другой), отдельным блоком остаётся только крупная картинка без текста рядом; маленькая картинка (значок, миниатюра `-150x150`, ширина меньше 500 px) всегда в тексте и с размерами, чтобы не растягиваться на всю ширину. Новый блок статьи начинается с заголовка h2, только когда в текущем набралось около 2000 знаков, соседние короткие блоки статьи склеиваются: страница из множества коротких разделов не превращается в столбик блоков (больше 100 блоков страница не получает). Встроенные видео, карты и неразобранные фрагменты попадают в статью ссылкой и в отчёт. Ограничения полей темы соблюдаются: длинный текст обрезается, длинная статья делится на несколько блоков по границам абзацев, лишние вопросы уходят во второй блок FAQ, ответ длиннее поля остаётся началом в вопросе, продолжение идёт статьёй под вопросами, у картинки без подписи `alt` берётся из названия страницы. Всё обрезанное и выброшенное перечислено в потерях страницы. Внутренние ссылки ведут на новые адреса, ссылки на файлы картинок, скачанные в медиатеку, ведут на копию в медиатеке. Пункт меню с якорем (`/#rec769263598`, `/#service`) ведёт на блок, в который попала эта часть страницы (такая часть начинает свой блок и не склеивается с соседним); если такого блока нет, на страницу с тем же названием или на страницу без якоря (с предупреждением). У SEO-заголовка отрезается имя старого сайта в конце («О нас - Кофейня Зерно»): ядро добавит имя нового; если остаётся только название страницы, поле пустое.

## Адреса и редиректы

- Адрес берётся из старого пути, если он подходит для AgeCMS (вложенность через `/` сохраняется, `.html`, `.php`, `index.php/` отбрасываются, кириллица транслитерируется). Иначе из адреса, предложенного CMS, или из названия.
- Записи блога ложатся в раздел, как у источника: раздел это папка адреса (`/news/x` в `news`, `/about/news/x` в `about/news`, папки дат `/news/2020/05/x` отбрасываются), иначе `blog`. Страница раздела это перенесённая страница с адресом папки (`/about/news/`), если её нет, она создаётся с блоком `child_pages`; запись становится её дочерней страницей. Пост Потоков Tilda `/blog/tpost/<uid>-slug` получает адрес `blog/slug` (без `tpost` и номера) и 301 со старого; пост в корне (`/tpost/...`) ложится под страницу ленты, которую называет сборщик, если она перенесена.
- Страница с пометкой сборщика `skip` (товар магазина, пустая служебная страница, корзина и оформление заказа WooCommerce) не создаётся, ссылки на неё остаются ссылками на старый сайт. Копия другой страницы (тот же `tilda_page_id`) не создаётся, её адреса получают 301 на перенесённую.
- Занятый адрес (страница, адрес модуля, страница в корзине): `-2`, `-3` или пропуск, по выбору; дочерние страницы идут за переименованным родителем. Главная заменяется только по галочке «Заменить главную».
- Редирект 301 ставится со всех старых адресов страницы, которые отличаются от нового: `/?p=12`, `/page.html`, `/index.php/...`. Адреса, которые ядро не примет (адрес существующей страницы, системный), показываются в отчёте.

## Точная копия

Два режима переноса. **«В блоки темы»** (описан выше) переносит содержимое, дизайн берётся у темы сайта. **«Точная копия»** сохраняет вид и поведение источника: страница выглядит и работает как исходная на 1280 px и на 390 px, оставаясь страницей AgeCMS. В админке режим выбирается переключателем (по умолчанию «Точная копия»), в консоли `--mode=exact|blocks` (по умолчанию `exact`), в навыке параметром `mode` (по умолчанию `blocks`).

**Откуда берётся копия.** Копию снимает программа `tools/capture` (Node.js 20 и Chrome, подробности в `tools/capture/README.md`): она открывает сайт как посетитель и собирает пакет (страницы, файлы, манифест, журнал). Есть три пути.
- **Кнопкой в админке («Импорт сайта»).** Владелец вводит адрес и нажимает «Импорт»: сервер запускает захват фоновым процессом, быстро осматривает сайт (платформа, сколько страниц, примерное время) и показывает предпросмотр с кнопкой «Начать перенос». Дальше захват идёт на сервере сам, страницу можно закрыть и вернуться: задание остаётся в списке, показывает страницы, файлы, объём и время, его можно остановить. Готовый пакет ставится как обычно (страницы, 301, откат одним действием). Нужны Node.js 20, Chrome и `proc_open` на сервере; если чего-то нет, страница пишет, чего именно и как поставить (`bin/install-capture.sh`), а кнопка «Проверить захват на сервере» запускает Chrome и открывает пустую страницу. Пути к `node` и Chrome берутся из настроек `capture.node` и `capture.chrome`, затем из переменных `AGECMS_NODE` и `AGECMS_CHROME`, затем из PATH и привычных мест.
- **Пакет с компьютера владельца.** `node tools/capture/capture.mjs https://old-site.ru --zip`, дальше zip загружается в админке (`capture_zip`) или передаётся консоли.
- **Консоль.** `import.php https://old-site.ru --apply` вызывает захват сам, если есть node и Chrome (`--capture-dir=ПАПКА` берёт готовый пакет, `--no-mobile`, `--no-verify` передаются захвату).
В режиме «точная копия» архив Tilda и HTML-файл без захвата не принимаются: сообщение объясняет, как получить пакет. Выгрузка WordPress (WXR) в этом режиме переносится в блоки с пометкой в отчёте.

**Захват на сервере: порядок и пределы.**
- Процесс отделён от запроса (`capture.mjs --detach`), пишет файл состояния с отметкой жизни; страница читает его раз в несколько секунд. Если отметка не обновляется 90 секунд (сервер перезапускали, процесс убит), задание помечается «прервано», а не висит.
- Один захват на сайт одновременно; второй не стартует, пока идёт первый.
- Пределы (настройки модуля): страниц (50 для точной копии), объём пакета (500 МБ), время (30 минут), память процесса (2048 МБ). Перед стартом проверяется свободное место. Превышение завершает захват с понятным сообщением, пакет из уже снятого можно импортировать.
- «Остановить захват» посылает процессу сигнал, при необходимости убивает его вместе с Chrome и удаляет временные файлы; сайт при этом не менялся. Процесс узнаётся по метке задания, чужой процесс с тем же номером не трогается.
- Для проверки на своих адресах (локальный сайт-источник) есть только аварийный переключатель разработчика: `--allow-private` в консоли или `AGECMS_IMPORT_ALLOW_PRIVATE=1` в окружении встроенного сервера `php -S`. В обычной работе он выключен, из админки включить его нельзя.

**Что получается.**
- Страница AgeCMS с одним системным блоком `site_copy` (его добавляет только ядро и импорт): в нём `<head>`, содержимое `<body>` и, если нужна, отдельная версия для телефона. Тема не участвует. Адрес, SEO-поля (название, описание, noindex), 301 со старых адресов, история изменений и откат работают как у любой страницы. Внутренние ссылки переписаны на новые адреса.
- Для поиска, карты сайта и `llms.txt` в блоке хранится видимый текст страницы.
- Файлы лежат в `assets/uploads/copy/<ключ>/` (ключ `j<номер задания>`), все внутренние адреса указывают туда. Внешними остаются только карты и ролики YouTube и Vimeo.
- Версия для телефона (если страницу под экран собирают скрипты) отдаётся по `?ag_view=m`; экраны уже 768 px перенаправляются на неё скриптом в `<head>`.
- Счётчики, трекеры и чаты не переносятся (Метрика, Google Analytics, пиксели Facebook и VK, Top.Mail.ru, виджеты чатов, статистика Tilda, кнопки соцсетей). Счётчик Метрики самого сайта AgeCMS подставляется ядром, как на любой странице.
- Формы: если форма отправляет данные простым способом, она подключается к заявкам AgeCMS (скрипт `assets/copy-forms.js`, раздел «Заявки»); иначе в отчёте строка «форма не подключена».

**Предпросмотр** показывает страницы, число файлов и мегабайты, сходство с оригиналом, найденное захватом (компьютер и телефон), убранные счётчики и судьбу каждой формы. **Откат** одним действием возвращает всё: страницы в корзину, редиректы, меню и файлы копии; файлы остаются, только если страницу, их использующую, изменили и она жива.

**Правка после импорта.**
- *Текст на странице.* Редактор (право редактировать страницы) на странице-копии нажимает «Править текст»: элементы подсвечиваются, на нужный нажимаем и меняем текст на месте, ссылку (адрес) или картинку (замена файлом из «Медиа» или загрузкой). Внизу «Сохранить», «Отменить правки», «Выйти из правки». Правка пишется в тот же документ страницы (`copy_body`, версия для телефона и текст для поиска обновляются), попадает в историю страницы и откатывается, как любое изменение.
- Что можно: заменить текст внутри размеченного элемента, адрес ссылки (`http`, `https`, `mailto`, `tel`, свой путь), адрес и описание (`alt`) картинки; у картинки при замене убираются `srcset` и ленивые атрибуты, чтобы показывалась новая. Тексты экранируются, адреса проверяются, скрипты и обработчики вставить нельзя.
- Чего нельзя (по замыслу): менять структуру (добавлять и удалять блоки, перетаскивать), форматирование (Enter и вставка с форматом отключены), `<picture>` и фоновые картинки CSS, текст, который собирает скрипт страницы. Если на странице нужного нет, правится код.
- Страница изменилась в другом окне после открытия редактора: сохранение отвечает 409, нужно перезагрузить страницу (сравнивается отпечаток версии). Если разметка не совпала с сохранённой, такая правка пропускается и пишется в ответе, ничего не угадывается.
- Роль редактора правит текст, но не код: `<head>` и `<body>` по-прежнему доступны только через «править код».
- *Код.* Страница «править код» (`/admin/m/importer/copy?slug=`, ссылка есть в отчёте и на странице редактирования): название, SEO-поля, `<head>` и `<body>` копии (и версия для телефона) в текстовых полях. Правка идёт через ядро, поэтому остаётся в истории и откатывается. Пустое содержимое не принимается.

**Безопасность.**
- Чужой код попадает на сайт только действием администратора (`system.manage`), в интерфейсе показано предупреждение.
- Захват на сервере открывает чужие адреса, поэтому от SSRF защищено каждое обращение браузера: схемы `file`, `chrome`, `ftp` и подобные запрещены; адрес сверяется после DNS по настоящему IP, а не по имени, и запрещены внутренние диапазоны (loopback, частные сети, link-local, 100.64.0.0/10, локальные IPv6, метаданные облака). Браузер ходит только через локальный прокси процесса: имена разрешает только прокси и закрепляет за ответом (подмена DNS между проверкой и запросом не проходит), перенаправления проверяются на каждом шаге, число и размер ответов ограничены, скачивание файлов в браузере выключено. Chrome запускается с песочницей (при невозможности её включить в окружении это видно в журнале), отдельным временным профилем и урезанным окружением (без секретов сайта). Файл на сервере по пути принимает только консоль: токен API такой путь не принимает.
- Пакет, снятый на сервере, проверяется как загруженный: каждая запись пакета проверяется: допустимые символы имени, без `..`, без серверных расширений (`.php`, `.phtml`, `.phar`, `.htaccess`, `.cgi`, `.pl`, `.py`, `.sh`), только известные типы файлов, предел записи 20 МБ для текстов, `realpath` внутри каталога копии. SVG очищается от `script`, `foreignObject`, `on*` и `javascript:`. Защиты от XXE, zip-slip и предел размера импорта остаются.
- Скрипты на страницах копии лежат на этом же сайте. У страниц копии своя политика CSP, остальной сайт остаётся со строгой.

**Кэш и заголовки.** Страницы копии не попадают в теневой кэш `assets/cache` (его отдаёт веб-сервер с общими заголовками, строгая CSP сломала бы копию): их всегда отдаёт PHP с заголовком `X-AgeCMS-Policy: copy`, своей CSP (`CopyPage::csp`), ETag и ответом 304; при входе администратора `Cache-Control: private, no-store`. Веб-сервер на этот заголовок реагирует так:
- Apache: `.htaccess` ставит строгую CSP только если `X-AgeCMS-Policy` не равен `copy`, и убирает служебный заголовок (`Header always unset`). Проверено на Apache с php-fpm.
- nginx: в `nginx.vhost.example` `map $upstream_http_x_agecms_policy $agecms_csp` выбирает политику, `fastcgi_hide_header` скрывает CSP и служебный заголовок от PHP, у `/assets/uploads/copy/` включён sandbox для документов. Пример проверен только по чтению (nginx на машине разработки нет).
- `php -S` с `tests/support/router.php` для тестов: файлы копии отдаёт роутер.

Файлы копии отдаёт веб-сервер как обычные загрузки; HTML, SVG и XML из каталога загрузок получают CSP с `sandbox`, чтобы нельзя было превратить загрузку в страницу сайта.

**Обновление и копии.** «Обновить» не пишет в `assets/uploads/` и не стирает файлы копии. `bin/backup.php` и резервная копия из админки кладут файлы копии в архив (`site-copy/<ключ>/...`).

## Тесты

```bash
php modules/importer/tests/run.php
```

Тесты идут на маленьких фикстурах (`tests/fixtures/`: WordPress REST и WXR, Tilda и архив экспорта, Битрикс в windows-1251, сайты разных CMS, обычный сайт с sitemap и robots.txt) без сети. Раннер модуля берёт все `tests/*Test.php`. Те же тесты запускаются вместе с тестами ядра: обёртки `tests/Importer*Test.php` ядра подключают каждый файл модуля по одному разу.

## Что известно

- Сайты, которые рисуют содержимое только скриптом в браузере (часть сайтов Wix, одностраничные приложения), отдают мало текста: переносится то, что есть в HTML.
- Каталоги товаров (OpenCart, Битрикс, WooCommerce, магазин Tilda) не переносятся: только страницы и новости. У HostCMS и тем OpenCart без стандартной разметки категория каталога может перенестись страницей с карточками.
- Файлы (PDF, документы) остаются ссылками на старый сайт.
- Картинки AVIF (Webflow) перекодируются в WebP, если GD сервера читает AVIF (PHP 8.1+ с libavif); иначе картинка остаётся ссылкой на старый сайт, это пишется в потери страницы.
- Zero Block Tilda и колонки конструкторов переносятся без расположения, с пометкой «перенесите вручную»: проверьте эти страницы после импорта. Формы во всплывающих окнах Tilda не переносятся, только пометка.
- При лимите страниц записям блога (Потоки Tilda, записи WordPress) отдаётся треть лимита, остальное страницам; остальные записи перечислены в предупреждении.
