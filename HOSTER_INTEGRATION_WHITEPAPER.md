# AgeCMS для хостинг-провайдеров

Краткий технический документ для тех, кто хочет добавить AgeCMS в каталог приложений или 1-click установщик. Все утверждения о нагрузке относятся к измерениям из [docs/BENCHMARK.md](docs/BENCHMARK.md); где измерений нет, это сказано.

## Почему сайту на AgeCMS нужно мало ресурсов

- Нет MySQL. Вся база это один файл `data/data.sqlite`. Бэкап и перенос это копирование файла (или `php bin/backup.php`).
- Публичные страницы это готовые `.html` в `assets/cache/`. Для посетителя без cookie `agecms_admin` и без строки запроса веб-сервер отдаёт файл, PHP не запускается. На замере с Apache и php-fpm одна страница из кэша обрабатывается за 0.11 мс против 0.72 мс при полном рендере.
- PHP работает только при первом показе страницы после правки, для форм, поиска, админки и API.
- Нет фоновых демонов. Нужен один cron в минуту: `php bin/queue-worker.php`.

## Требования

| Что | Значение |
| --- | --- |
| PHP | 8.1 и новее, FPM или `mod_php` |
| Расширения | обязательные `pdo_sqlite`, `mbstring`, `json`; рекомендуемые `gd` (WebP), `curl`, `sodium` или `openssl` (подпись обновлений), `zlib`, `zip` |
| SQLite | 3.35+ с FTS5 (для `VACUUM INTO` и поиска) |
| Web | Apache с `mod_rewrite`, `mod_headers`, `AllowOverride All`, либо nginx по `nginx.vhost.example` |
| Диск | запись в `data/`, `assets/cache/`, `assets/uploads/` |
| Память | php-fpm по умолчанию достаточно, отдельных лимитов нет |

Файловая система с блокировками (`flock`) обязательна: очередь записи и кэш на них держатся. Сетевые ФС без блокировок (часть NFS-конфигураций) не подходят для каталога `data/`.

## Установка без участия пользователя

```bash
git clone <репозиторий> "$DOCROOT"
cd "$DOCROOT"
php bin/install.php --url=https://$DOMAIN --name="$SITE_NAME" --admin="$USER" --password="$PASSWORD" --no-demo
(crontab -l; echo "* * * * * php $DOCROOT/bin/queue-worker.php") | crontab -
```

Установщик не работает по вебу сам по себе: автоматического создания базы на первом запросе нет, чужой посетитель не может «захватить» свежую установку. Если панель хостинга ставит скрипт по вебу, она кладёт в `data/install.key` случайную строку от 32 символов и открывает `/admin/install.php?key=...`. После установки создаётся `data/install.lock`, и оба пути закрыты навсегда.

Пароль администратора в базе хранится как хэш (`password_hash`), в журналах его нет.

## Безопасность в общей среде

- Каталог `data/` закрыт в `.htaccess` (`Require all denied`) и в конфиге nginx. Проверено на Apache: прямые запросы к `/data/`, `/core/`, `/bin/`, `/modules/`, `/tests/` и скрытым файлам дают 403 или 404.
- `assets/cache/` и `assets/uploads/` не исполняют PHP.
- Исходящие запросы (вебхуки, IndexNow, импорт картинок) идут только на публичные адреса по HTTPS, порты 80 и 443; адрес разрешается один раз и закрепляется, поэтому подмена DNS между проверкой и запросом не работает. Закрыты частные диапазоны, loopback, link-local и облачные адреса метаданных.
- Секреты (мастер-ключ, токен Telegram) лежат в `data/config.php` с правами 0600, не в базе.
- Агентский доступ по Bearer-токену, токены хранятся как SHA-256, роли `viewer`/`editor`/`admin`, лимит 120 вызовов в минуту на токен.

## Обновление

Код ядра заменяется целиком: `core/`, `admin/`, `bin/`, `assets/` (кроме `assets/uploads/` и `assets/cache/`), `themes/default/`, `index.php`, `.htaccess`. Каталоги `data/`, `assets/uploads/`, свои темы и модули остаются. Схема базы обновляется миграциями автоматически при первом обращении по `PRAGMA user_version`. Перед обновлением панель может вызвать `php bin/backup.php`. Подписанные модули после обновления ядра проверяются заново. После замены стоит выполнить `php bin/clear-cache.php`, чтобы страницы пересобрались с новым кодом.

### Как сайт узнаёт о новой версии

Версия установленного ядра лежит в `core/release.json`:

```json
{ "version": "1.0.0", "date": "2026-10-28", "notes": "Что изменилось", "url": "https://.../changelog" }
```

Файл последней версии лежит в ветке `releases` этого репозитория: https://raw.githubusercontent.com/likvp/AgeCMS/releases/release.json. Это адрес проверки по умолчанию, поэтому сайт видит новые версии без настройки. Другой адрес (свой сервер обновлений хостера, форк) задаётся в админке («Система», «Версия ядра») или командой `php bin/config.php set updates.url https://.../release.json`. Раз в сутки сайт после ответа на запрос скачивает этот файл (не больше 64 КБ, только публичные адреса, как у вебхуков), запоминает ответ в `data/updates.json` и, если версия там выше своей, показывает администратору плашку на всех страницах админки, а агенту отдаёт её в `get_site_structure` (`core.newer`). При ошибке следующая попытка через час. Пустой адрес выключает проверку, ничего никуда не уходит.

### Обновление из админки

В «Системе» администратор нажимает «Обновить до x.y.z» (или `php bin/update.php --install`). Агент с токеном роли admin делает то же через MCP: `check_core_update`, `update_core`, `rollback_core`, `set_core_updates` (адрес и автообновление); у editor и viewer этих инструментов нет. Галочка «Обновлять автоматически» (`updates.auto`, по умолчанию выключена) ставит новую версию сама, в течение суток после выхода; неудачная попытка той же версии повторяется через сутки.

Что происходит:

1. Сайт заново читает `release.json` и проверяет подпись над версией, SHA-256 и размером пакета. Подписей две над одними и теми же байтами: Ed25519 (ключ `agecms-2026`, проверяется расширением sodium) и ECDSA P-256 (ключ `agecms-2026-p256`, проверяется openssl, для хостингов, где PHP собран без sodium). Хватает одной верной подписи доверенным ключом. Доверенные ключи лежат в `core/release-keys.json` и в `updates.trusted_keys` конфига. Без подписи известным ключом пакет не скачивается: тот, кто подменит адрес или файл, не сможет выполнить свой код на сайтах.
2. Скачивается пакет (до 30 МБ, без перенаправлений, только публичный https), сверяются размер и SHA-256.
3. Пакет распаковывается в память. Каждый путь проверяется: писать можно только в `core/`, `admin/`, `bin/`, `assets/` (кроме `uploads/` и `cache/`), `themes/default/`, `index.php`, `.htaccess`. Внутри должен быть `core/release.json` той же версии.
4. Делается копия базы (как кнопка «Сделать бэкап») и копия заменяемых файлов в `data/backups/core-<версия>-<время>.json.gz` (хранятся три последние).
5. Файлы пишутся рядом и переименовываются поверх старых. Если хоть один не записался, прежние файлы возвращаются, новые удаляются.
6. Сбрасываются OPcache и кэш страниц. Схема базы догоняет новую версию на следующем запросе.

Файлы, которых в новой версии нет, остаются на месте. Вернуть прежние файлы: `php bin/update.php --rollback` (база не откатывается: старый код новых колонок не замечает).

Чтобы кнопка работала, PHP должен иметь право писать в файлы сайта (на общем хостинге с ISPmanager и php-fpm от пользователя сайта это так). Если права нет, нет zlib или нет ни sodium, ни openssl, «Система» пишет, что мешает, и кнопку не показывает.

### Выпуск новой версии

```bash
php bin/release.php --version=1.1.0 --notes="Что изменилось" --key=~/.config/agecms/release-ed25519.key --p256-key=~/.config/agecms/release-p256.pem
```

Команда записывает версию в `core/release.json`, собирает `dist/agecms-1.1.0.json.gz` (все файлы ядра из git) и подписанный `dist/release.json`. Дальше:

```bash
git commit -am "версия 1.1.0" && git push
bin/publish-release.sh
```

`bin/publish-release.sh` кладёт оба файла в ветку `releases` и пушит её. Через несколько минут (кэш GitHub) сайты увидят новую версию при ближайшей суточной проверке, кнопка «Проверить сейчас» покажет её сразу.

Ключи подписи `agecms-2026` (Ed25519) и `agecms-2026-p256` (ECDSA P-256): закрытые части у Лерка на Mac в `~/.config/agecms/release-ed25519.key` и `~/.config/agecms/release-p256.pem` и в его хранилище Obsidian (`Pass/`, карточка «AgeCMS доступ»). Без второго ключа `bin/release.php` не собирает выпуск, иначе сайты без sodium не смогли бы его поставить. В репозиторий и на серверы закрытый ключ не кладётся. Новая пара делается `php bin/sign-module.php --keygen=<файл>`, открытая часть добавляется в `core/release-keys.json` и уезжает на сайты с очередной версией, подписанной ещё старым ключом.

## Что в этом документе не обещано

- Нет измерений на общем (shared) хостинге с медленным диском и на нескольких сотнях сайтов на одном сервере.
- nginx проверен на одном сервере (1.24). Тесты проходят на PHP 8.1-8.5 (`bin/test-matrix.sh`).
- Обновление из админки проверено на тестовых пакетах и копии сайта, не на общем хостинге. Пока идёт замена файлов (доли секунды), параллельный запрос может застать смесь старых и новых файлов.
