# Модули AgeCMS: справочник разработчика

Модуль это папка в `modules/<имя>/` с `manifest.json`, подписью `manifest.json.sig` и классом, который реализует `ModuleInterface`. Подпись ставит `php bin/sign-module.php <имя>`. Любая правка файла после подписи блокирует модуль целиком.

## Свои модули без подписи

Модуль можно написать самому (или попросить ИИ-агента) и поставить без подписи.

| Состояние в «Системе» | Что это | Работает |
| --- | --- | --- |
| зелёное «подпись проверена», «подписан этим сайтом» | подписан ключом сайта (`php bin/sign-module.php <имя>` или кнопка «Подписать») | да |
| зелёное «подпись проверена», «подпись разработчика <ключ>» | подписан Ed25519 ключом из `trusted_publishers` | да |
| красное «подпись не проверена» | нет `manifest.json.sig`: свой модуль | да, и пока он есть, администратор видит красную плашку на всех страницах админки |
| красное «заблокирован» | подпись есть, но не сходится, или файл изменён после подписи (так выглядит подмена), или модуль сломан | нет |
| «выключен» | выключен в админке (`modules.disabled`) | нет |

- Поставить: архив `.zip` в «Системе» («Загрузить модуль», модуль в корне архива или в одной папке), инструмент агента `install_module` (`files`: путь => текст, или `zip_base64`), или папкой в `modules/`. «Заменить, если уже есть» обновляет модуль, прежняя папка остаётся в `data/module-backups/` (три последние).
- Выключить, включить, удалить: кнопки в «Системе» и инструменты `disable_module`, `enable_module`, `delete_module` (только роль admin). Удаление переносит папку в `data/module-backups/`, таблицы `mod_<имя>_*` остаются.
- Подписать ключом сайта: кнопка «Подписать» у модуля без подписи (только человек в админке, у агента такого инструмента нет). После подписи изменение любого файла блокирует модуль, поэтому для правки снова уберите `manifest.json.sig` или подпишите заново.
- Для модуля без подписи ядро само составляет список файлов, навыков (`skills/*.json`) и миграций (`migrations/*.sql` по порядку имён), как это сделала бы подпись. Нужны `manifest.json` с `name` (как папка), `class` и `entry` (по умолчанию `Module.php`).
- Все ограничения ядра (адреса, миграции только над `mod_<имя>_*`, проверки `POST`, cookie) действуют и на модули без подписи. Но код модуля выполняется с правами сайта: ставьте только то, чему доверяете.
- Сайт, где должен работать только подписанный код: `php bin/config.php set modules.allow_unsigned false`. Тогда модуль без подписи блокируется.

## События

Модуль подписывается на события в `register()`: `EventBus::listen('lead.created', fn(array $payload) => ...)`. Сбой слушателя пишется в журнал и не доходит до кода, который вызвал событие.

| Событие | Когда | Данные |
| --- | --- | --- |
| `lead.created` | сохранена заявка | данные заявки |
| `background.tick` | периодически, см. ниже | `time` (unix-время), `deadline` (`microtime(true)`, до которого надо закончить) |

### background.tick

Работа по расписанию без cron: рассылки, синхронизация с внешней системой. Событие поднимает `Background::tick()` после того, как ответ посетителю уже отправлен:

- не чаще одного раза в 30 секунд на весь сайт и никогда не одновременно в двух запросах (блокировка файла `.tick-modules` в папке очереди);
- запускается после посещения страницы, дошедшего до PHP (запрос `GET`/`HEAD`, а также сигнал просмотра `POST /_/hit`, который шлёт `assets/app.js` даже со страницы, отданной из кэша), и после сохранения в админке или через API;
- слушатель сам решает, пора ли ему работать (хранит время последнего запуска у себя) и обязан закончить до `deadline`; остаток доделывает следующий тик;
- декларативные вебхуки (`integration_*`) для этого события не вызываются, на него подписываются только модули;
- если сайт совсем без посетителей, тик не придёт: для точного срока откройте любую страницу сайта из внешнего планировщика (например, `curl` раз в минуту).

Исключение в слушателе пишется в журнал событием `event.listener_failed`, остальные слушатели продолжают работу.

## Адреса модуля (routes)

Модуль, который показывает свои страницы (кабинет, каталог, отписка из рассылки), объявляет адреса в подписанном `manifest.json` и реализует `RoutedModuleInterface` с методом `handle(ModuleRequest): ModuleResponse`:

```json
"routes": [
  {"path": "/kabinet", "methods": ["GET"]},
  {"path": "/kabinet/vhod", "methods": ["GET", "POST"], "rate": {"limit": 5, "window": 60}},
  {"path": "/katalog/{id}", "methods": ["GET"], "cache": "public", "max_age": 300}
]
```

| Поле | Значение |
| --- | --- |
| `path` | до 6 частей из строчных латинских букв, цифр, `-` и `_`; часть `{имя}` принимает буквы, цифры, `-`, `_` (до 64 знаков) и приходит модулю как `$request->param('имя')`; первая часть не может быть `{имя}` |
| `methods` | `GET` и/или `POST`; `HEAD` обслуживается как `GET` |
| `rate` | своё ограничение запросов с одного IP: `limit` 1-600, `window` 10-3600 секунд. Без поля: 120 в минуту для чтения, 10 в минуту для адреса с `POST` |
| `cache` | `private` (по умолчанию: `Cache-Control: private, no-store`) или `public` (только `GET`, с `max_age` 1-86400; ответ без cookie) |
| `indexable` | `true` только вместе с `cache: public`: успешная страница адреса отдаётся поисковикам (`index, follow`, `canonical` на сам адрес без параметров, описание из `ModuleResponse::withDescription()`). Без флага страницы модулей остаются `noindex`. Страницы ошибок `noindex` всегда |

Что делает ядро, а модуль не может отключить:

- Адреса получают подписанные модули и свои модули без подписи. Заблокированный (подпись не сходится, файл изменён после подписи) или выключенный модуль не получает ни адресов, ни миграций.
- Недопустимы адреса ядра (`/admin`, `/assets`, `/search`, `/_`, `/index`, `/sitemap`, `/robots`, `/llms`, `/agent`, `/data`, `/modules`, `/themes` и другие служебные), существующие страницы сайта и адреса другого модуля, в том числе пересечение через `{имя}`. Конфликт блокирует модуль при загрузке (причина видна в списке модулей и в журнале `module.blocked`); при споре двух модулей адрес остаётся у того, чьё имя раньше по алфавиту. Страницу с адресом, который занял модуль, создать или переименовать нельзя.
- `POST` проходит проверку: тот же сайт (`Origin`, `Sec-Fetch-Site`), подписанный токен времени (в форму кладётся `<?= ag_module_form_fields() ?>`; модуль поля `token` не видит) и ограничение запросов. Ограничение действует и на `GET`.
- Ответ получает заголовки безопасности ядра. Модуль выбирает только статус, страницу (`ModuleResponse::html($title, $bodyHtml)`, рисуется в теме через `Renderer::shell`, поэтому с `noindex`), JSON или переадресацию (302 или 303 на адрес этого же сайта), а также свои cookie: ядро добавляет имени префикс `<модуль>_`, `HttpOnly`, `SameSite=Lax`, `Secure` на https. Модуль читает только свои cookie, сессия админки ему недоступна.
- Страницы модулей никогда не попадают в теневой кэш `assets/cache`.
- Исключение в обработчике не показывается посетителю: ему общая страница с кодом 500, подробности в журнале `module.route_failed`.
- Инструменты агента `<модуль>__<навык>` работают как раньше.

## Миграции (migrations)

Файлы `migrations/*.sql` модуля подписываются вместе с манифестом (`php bin/sign-module.php <модуль>` сам вносит их в `migrations` по порядку имён: `001_init.sql`, `002_...`).

- Файл выполняется один раз; все новые файлы модуля выполняются в одной транзакции, при сбое не применяется ничего.
- Состояние хранится отдельно от схемы ядра: таблицы `module_migrations` (какой файл, с каким хешем) и `module_state`. Они появляются только у сайта, где есть модуль с миграциями.
- Разрешены `CREATE TABLE/INDEX/VIEW`, `ALTER TABLE`, `DROP`, `INSERT`, `UPDATE`, `DELETE` и только над объектами с именем `mod_<модуль>_...`. Триггеры, `PRAGMA`, `ATTACH`, управление транзакциями и временные таблицы запрещены. После выполнения ядро сверяет, что его собственные таблицы не изменились.
- Применённый файл менять нельзя: модуль будет заблокирован («applied migration ... was changed afterwards»). Новое изменение схемы кладётся в новый файл.
- Сбой отключает модуль, пишется `module.migration_failed`. Повторная попытка только после новой подписи исправленного модуля, поэтому сайт не пробует миграцию на каждом запросе.

## Письма: HTML и заголовки рассылки (Mailer)

`Mailer::send($to, $subject, $body, $options = [])`. Старый вызов с тремя аргументами работает как раньше: письмо из одной текстовой части.

```php
Mailer::send($email, 'Новые поступления', $text, [
    'html' => $htmlBody,
    'headers' => [
        'List-Unsubscribe' => '<https://site.ru/otpiska/' . $token . '>',
        'List-Unsubscribe-Post' => 'List-Unsubscribe=One-Click',
        'Reply-To' => 'office@site.ru',
        'Precedence' => 'bulk',
    ],
]);
```

- `html`: письмо становится `multipart/alternative`, `$body` остаётся текстовой версией для клиентов без HTML. Обе части в base64 UTF-8.
- `headers`: любые заголовки, кроме системных (`From`, `To`, `Cc`, `Bcc`, `Subject`, `Date`, `Message-ID`, `MIME-Version`, `Return-Path`, `Sender`, `Content-*`).
- Защита: имя заголовка только латиница, цифры и дефис; значение без переводов строк и управляющих символов, не пустое, до 900 знаков. Нарушение это `AgeCMSException`, письмо не уходит (исправлять молча не пытаемся: перевод строки в значении признак подделки).
- Проверяются форматы: `List-Unsubscribe` только `<https://...>` и/или `<mailto:...>` через запятую, `List-Unsubscribe-Post` только `List-Unsubscribe=One-Click`, `Reply-To` должен быть адресом.
- Заголовки идут одинаково в `mail()`, SMTP и `log`-транспорт (файлы в `data/outbox`).

## Адреса модуля в sitemap.xml и IndexNow

Публичные страницы модуля (карточка товара, статья) попадают в `sitemap.xml`, если модуль реализует `SitemapModuleInterface` (он расширяет `RoutedModuleInterface`) и отдаёт адреса:

```php
public function sitemapUrls(): iterable
{
    foreach ($this->newestItems(1000) as $item) {
        yield ['path' => '/katalog/' . $item['id'], 'lastmod' => $item['updated_at']];
    }
}
```

- Ядро принимает адрес только если его обслуживает маршрут **этого же модуля** с `"cache": "public"` и `"indexable": true`. Чужой адрес, страница сайта, `/admin/`, адрес с лишними символами, повтор и непубличный маршрут отбрасываются (в журнал `sitemap.rejected`).
- От одного модуля берётся не больше `ModuleSitemap::LIMIT` (1000) адресов, поэтому отдавайте сначала самые свежие. Для всех модулей вместе не больше 5000.
- `lastmod` необязателен, берутся первые 10 знаков вида `2026-10-27`.
- Заблокированный модуль (подпись не совпала, сбой миграции) ничего не добавляет. Сбой в `sitemapUrls()` пишется в журнал `sitemap.module_failed`, карта сайта остаётся рабочей.
- Об изменении адреса сообщают поисковикам так: `ModuleSitemap::ping('katalog', ['/katalog/42'])`. Правила те же; пинг уходит через IndexNow после ответа (только на настоящем https-домене, как и для страниц). Вернётся число принятых адресов.

## Страницы модуля в админке (admin)

Сотрудник работает в админке, а модуль не видит её сессию (так и задумано). Чтобы у модуля был свой раздел («Рассылки»: список, форма), он объявляет страницы в подписанном `manifest.json` и реализует `AdminModuleInterface`:

```json
"admin": [
  {"path": "/", "title": "Рассылки", "permission": "content.write"},
  {"path": "/campaigns/{id}", "title": "Кампания", "permission": "content.write", "methods": ["GET", "POST"]},
  {"path": "/send", "title": "Отправить", "permission": "system.manage", "methods": ["POST"]}
]
```

```php
final class Module implements AdminModuleInterface
{
    public function handleAdmin(ModuleRequest $request, Actor $actor): ModuleResponse
    {
        // $request->path: "/admin/m/mailing/campaigns/3", $request->param('id'): "3", $actor->name / ->role: кто открыл
        return ModuleResponse::html('Кампания', '<form method="post">' . ag_admin_csrf_field() . '...</form>');
    }
}
```

Страницы живут по адресу `/admin/m/<модуль><path>`. Пункт меню «title» появляется в боковом меню админки для тех, у кого есть право.

**Что делает ядро (модуль этого не касается и не может отключить):**

- Страница открывается только вошедшему пользователю с правом из `permission`. Без входа: переход на `/admin/` (GET) или 403 (POST). Без права: страница «Нет доступа» (403), модуль не вызывается. Заблокированный пользователь это тот же «без входа».
- `permission` одно из `content.read`, `content.write`, `cache.clear`, `search`, `skills.run`, `system.manage`. Роль «редактор» имеет `content.*`, `cache.clear`, `search`; администратор всё; поэтому `system.manage` видит только администратор.
- Методы только `GET` и/или `POST` (`methods`, по умолчанию `GET`). Страница не отвечает на метод, которого нет в списке (404), остальные методы дают 405.
- POST проходит CSRF админки: в форме нужно поле `ag_admin_csrf_field()`; запрос без токена получает 403, поле `csrf` до модуля не доходит. Публичный токен форм модулей (`ag_module_form_fields()`) здесь не подходит.
- Не больше 300 запросов в минуту на пользователя.
- Модуль получает тот же `ModuleRequest`, но `cookies` всегда пустой: ни сессии админки, ни других cookie.
- Ответ тот же `ModuleResponse`. HTML рисуется внутри админки (заголовок экранируется, тело печатается как есть, экранируйте сами), `json` отдаётся как есть, `redirect` разрешён только на страницу этого же модуля (302 или 303). Ответ с cookie, чужим редиректом или недопустимым статусом заменяется ошибкой 500 с записью `module.admin_failed` в журнале; исключение модуля показывается так же, без текста исключения.
- Страницы не кэшируются (`Cache-Control: no-store`).

**Проверка манифеста.** Модуль блокируется целиком, если `admin` не список (до 20 страниц), у страницы нет `path`, `title` или `permission`, есть лишнее поле, путь не начинается с `/` или длиннее 4 сегментов (буквы a-z, цифры, `-`, `_` или `{имя}`), заголовок пустой или длиннее 60 знаков, право или метод неизвестны, две страницы перекрываются, либо в меню (`menu: true`) попала страница с `{}` или без GET. По умолчанию в меню идут страницы с GET без `{}`; лишние скрывайте через `"menu": false`. Если модуль объявил `admin`, но не реализует `AdminModuleInterface`, он блокируется при загрузке.

### Живые части страницы: опрос и шаги без перезагрузки

Своих скриптов у страницы модуля нет (политика безопасности пускает только скрипты сайта, без inline), поэтому опрос делает `assets/admin/admin.js` ядра. Модуль только размечает элемент:

```html
<!-- GET каждые 2 с: прогресс фоновой работы -->
<div data-ag-poll="/admin/m/mailing/progress?id=5" data-ag-poll-interval="2000">...</div>

<!-- POST с CSRF-токеном админки: каждый запрос делает порцию работы, повтор, пока не готово -->
<div data-ag-step="/admin/m/importer/job?id=5&action=step" data-ag-step-interval="600">...</div>
```

- Адрес только этого сайта и только страницы модулей (`/admin/m/...`), иначе элемент не опрашивается. Интервал в миллисекундах: `data-ag-poll-interval` (по умолчанию 2000, не меньше 1000), `data-ag-step-interval` (не меньше 200). Следующий запрос уходит после ответа на предыдущий, наложений нет. Опрос GET пропускает такты, пока вкладка скрыта; шаги идут и в фоне.
- `data-ag-step` шлёт `POST` с полем `csrf` (берётся из `data-ag-csrf` элемента, из ближайшей формы или из любого поля `csrf` на странице: оно есть на каждой странице админки). Параметры шага передавайте в адресе (`?id=5&action=step`), модуль читает их из `$request->query`. Это и есть работа порциями без cron: пока страница открыта, каждый ответ делает следующий шаг.
- Каждый такой запрос несёт заголовок `X-AgeCMS-Poll: 1`. Модуль видит это как `$request->poll === true` и может вернуть только меняющуюся часть.
- **Ответ HTML.** Ядро отдаёт тело ответа модуля без админки вокруг (заголовок `X-AgeCMS-Fragment: 1`, те же заголовки безопасности, `no-store`), а скрипт ставит его на место содержимого элемента. Вставка как HTML безопасна: это то же, что модуль напечатал бы на странице (экранирует он сам), а inline-скрипты и обработчики в нём не выполняются из-за политики безопасности (`script-src 'self'`, без nonce и `unsafe-inline`), так что фрагмент не получает больше прав, чем страница. Формы с `data-confirm` во фрагменте работают (обработчик общий), вложенные `data-ag-poll`/`data-ag-step` запускаются.
- **Конец.** Элемент `[data-ag-done]` во фрагменте останавливает опрос. Его значение `reload` перезагружает страницу, адрес `/admin/...` открывает этот адрес (например страницу с готовым отчётом), пустое просто останавливает.
- **Ответ JSON** (`ModuleResponse::json`): `{"done": false, "html": "...", "fields": {"sent": 40, "total": 120}, "location": "/admin/m/...", "reload": false}`. `html` заменяет содержимое, `fields` заполняют элементы `[data-ag-field="sent"]` внутри (текст, а у `progress`, `meter`, `input` значение; `data-ag-max="total"` берёт `max` из другого поля), `done: true` останавливает, `location` или `reload` как у `data-ag-done`.
- **Ошибки.** Ответ 4xx или 500 показывается (это фрагмент модуля или ядра: «Сессия устарела», «Нет доступа») и опрос останавливается. 429 и 502-504 или обрыв связи: повтор с растущей паузой, после шести неудач сообщение «Нет связи с сервером». Ответ без `X-AgeCMS-Fragment` (сессия закончилась, вход в админку) перезагружает страницу.
- Без JavaScript ничего не происходит: оставьте запасной путь, например `<noscript><meta http-equiv="refresh" content="2;url=..."></noscript>` или ссылку «обновить».

```php
public function handleAdmin(ModuleRequest $request, Actor $actor): ModuleResponse
{
    if ($request->method === 'POST' && ($request->query['action'] ?? '') === 'step') {
        $state = Job::step((int)$request->query['id'], microtime(true) + 8);   // порция работы
        $part = '<progress max="' . $state['total'] . '" value="' . $state['done'] . '"></progress>'
            . ($state['finished'] ? '<span data-ag-done="/admin/m/mymod/report?id=' . (int)$state['id'] . '" hidden></span>' : '');
        return $request->poll ? ModuleResponse::html('Шаг', $part) : ModuleResponse::redirect('/admin/m/mymod/');
    }
    // ...
}
```

### Вкладки на странице модуля

Страница длиннее трёх экранов делится на вкладки. Компонент ядра `AdminTabs` рисует их ссылками: текущая вкладка в адресе (`?tab=`), поэтому работает без JavaScript, переживает перезагрузку и на неё можно дать ссылку. Так же устроены «Настройки» самой админки.

```php
use AgeCMS\AdminTabs;

public function handleAdmin(ModuleRequest $request, Actor $actor): ModuleResponse
{
    $tabs = ['key' => 'Ключ', 'login' => 'Вход', 'tariffs' => 'Тарифы', 'show' => 'Что показывать'];
    $tab = AdminTabs::current($tabs, $request->query['tab'] ?? null); // неизвестная или пустая: первая
    $body = AdminTabs::nav($tabs, $tab, $request->path);
    $body .= '<form method="post">' . ag_admin_csrf_field() . AdminTabs::field($tab) . '...</form>';
    return ModuleResponse::html('Настройка ЛК', $body);
}
```

`nav()` добавляет `?tab=` к адресу (или `&tab=`, если в нём уже есть запрос) и экранирует подписи. `field()` кладёт в форму скрытое поле `tab`: после POST модуль знает, на какую вкладку вернуться (например, `ModuleResponse::redirect($request->path . '?tab=' . $tab)`). Стили вкладок уже есть в админке, свои не нужны.

## Настройки модуля (settings)

Всё, что владелец сайта должен менять без правки файлов (имя отправителя, сколько писем за запуск, ключ внешнего сервиса), модуль объявляет в подписанном `manifest.json`. В разделе «Система» у модуля появляется кнопка «Настройки» с готовой формой, только для администратора.

```json
"settings": [
  {"key": "from_name", "label": "Имя отправителя", "type": "text", "default": "Карат", "length": 60, "help": "Видно в письме"},
  {"key": "batch", "label": "Писем за запуск", "type": "number", "min": 1, "max": 200, "default": 20},
  {"key": "enabled", "label": "Рассылки включены", "type": "bool"},
  {"key": "mode", "label": "Режим", "type": "select", "options": ["тест", "боевой"]},
  {"key": "footer", "label": "Подвал письма", "type": "textarea"},
  {"key": "api_key", "label": "Ключ сервиса", "type": "secret"}
]
```

```php
$batch = ModuleSettings::get('mailing', 'batch');   // сохранённое значение или default из манифеста
$all = ModuleSettings::all('mailing');
```

- Типы: `text`, `textarea`, `number` (`min`, `max`), `bool`, `select` (`options`), `secret`. Необязательные: `default`, `help`, `length` (по умолчанию 255 и 5000 для `textarea`).
- Значения проверяются по описанию до записи: число в диапазоне, значение `select` из списка, длина, без управляющих символов. Неописанные поля формы игнорируются. Нарушение не меняет ничего и показывается ошибкой.
- Хранение: `data/config.php` (права 0600), раздел `module_settings.<модуль>.<ключ>`. Не в базе данных, поэтому копия базы и агент через API их не видят.
- `secret` в форме никогда не показывается: поле пустое, оставить пустым значит не менять, отдельная галочка стирает значение. У `secret` нет значения по умолчанию.
- Манифест подписан, поэтому описание полей нельзя изменить без новой подписи. Неверное описание (неизвестный тип, повтор ключа, `default` не подходит к типу, `min` больше `max`, лишнее поле) блокирует модуль.

## Файлы со страницы админки (upload)

Страница модуля в админке (только `POST`) может принимать файлы: картинку для рассылки, прайс в CSV, PDF, файл выгрузки другой CMS (XML) или архив (ZIP). Страница объявляет это в манифесте, без объявления файлы игнорируются:

```json
{"path": "/import", "title": "Загрузить прайс", "permission": "content.write", "methods": ["POST"], "menu": false,
 "upload": {"kinds": ["csv", "image"], "max_kb": 2048, "max_files": 3}}
```

Форма: `<form method="post" enctype="multipart/form-data">` с `ag_admin_csrf_field()`. В модуле:

```php
foreach ($request->files as $file) {          // ModuleUpload
    $file->name; $file->kind; $file->mime; $file->size;
    $text = $file->contents();                 // для CSV, разобрать на месте
    $kept = $file->store();                    // приватная папка data/module_files/<модуль>/, имя возвращается
    $mediaName = $file->toMedia();             // только картинка: в медиатеку сайта (WebP, уменьшение)
}
$path = ModuleUpload::stored('mailing', $kept); // найти сохранённый файл позже; null для чужого или неверного имени
```

- Допустимые виды: `image` (JPEG, PNG, WebP, GIF; SVG нельзя), `pdf`, `csv` (UTF-8 без нулевых байтов), `xml` и `zip` (файлы выгрузки, ниже). Вид определяется по **содержимому файла**, имя и тип от браузера не учитываются: скрипт с именем `a.png` отклонится.
- Лимиты страницы: `max_kb` (1 до 10240, по умолчанию 2048), `max_files` (1 до 10, по умолчанию 1). Ещё действуют `upload_max_filesize` и `post_max_size` PHP (на многих хостингах 2 МБ и 8 МБ), при превышении пользователь видит понятное сообщение с этими значениями, а не «сессия устарела».
- Нарушение останавливает запрос до модуля: страница «Данные не приняты» (400) внутри админки, ничего не сохраняется. Проверки входа, права и CSRF идут раньше.
- Сохранённые файлы лежат в `data/module_files/<модуль>/` под случайным именем (права 0600), по сети недоступны, чужой модуль их не находит.

**Файлы выгрузки: `xml` и `zip`.** Для модулей, которые переносят сайт или принимают большой архив (выгрузка WordPress, экспорт проекта Tilda):

```json
{"path": "/upload", "title": "Загрузка файла импорта", "permission": "system.manage", "methods": ["POST"], "menu": false,
 "upload": {"kinds": ["xml", "zip"], "max_kb": 51200, "max_files": 1}}
```

- Вид определяется по сигнатуре, а не по имени: `zip` начинается с `PK\x03\x04` (и, если в PHP есть `zip`, открывается как архив и не пуст, иначе «архив повреждён или пуст»), `xml` начинается с `<?xml` или `<rss` (допускаются метка порядка байтов UTF-8 и пробелы перед ними, нулевых байтов в начале нет). HTML с именем `export.xml` или скрипт с именем `a.zip` отклоняются. Тип у модуля: `application/xml` или `application/zip`.
- Размер: у страницы с `xml` или `zip` `max_kb` до 524288 (512 МБ, `ModuleUpload::EXPORT_MAX_KB`), по умолчанию 51200 (50 МБ, `EXPORT_DEFAULT_KB`). Картинки, PDF и CSV на такой странице по-прежнему не больше 10 МБ (`SMALL_MAX_KB`).
- Сколько реально пройдёт на этом сервере: `ModuleUpload::maxBytes('<модуль>', '/upload')` (байты: `max_kb` страницы, уменьшенный до `upload_max_filesize` и `post_max_size`; 0, если страница файлов не принимает). Покажите это рядом с полем: `ModuleUpload::sizeText($bytes)` даёт «50 МБ». Если файл больше, предложите положить его по FTP в папку модуля под `data/`.
- Такой файл никогда не попадает в публичные папки: `store()` кладёт его в `data/module_files/<модуль>/` (закрыта для веба в `.htaccess` и `nginx.vhost.example`), `toMedia()` его не принимает. Модуль распаковывает архив или копирует файл тоже только под `data/` (например `data/<модуль>/`), а ненужную больше копию удаляет: `ModuleUpload::delete($module, $name)`.

```php
$file = $request->files[0] ?? null;                  // kind 'xml' или 'zip'
if ($file !== null) {
    $name = $file->store();
    $path = ModuleUpload::stored('importer', $name);  // data/module_files/importer/<случайное>.xml
    // ... разобрать или скопировать в свою папку под data/ ...
    ModuleUpload::delete('importer', $name);
}
```

Форма такая же: `enctype="multipart/form-data"`, поле `<input type="file" name="..." accept=".xml,.zip">`, `ag_admin_csrf_field()`. Поле файла может быть необязательным: без файла страница получает обычный POST с `files` пустым, так одна форма принимает и адрес сайта, и файл.

## Карта и другие встроенные рамки (frame-src)

Политика безопасности (`Content-Security-Policy`) по умолчанию запрещает чужие рамки на странице. Разрешены только виджеты карт по точным адресам, больше ничего:

- `https://yandex.ru/map-widget/` и `https://yandex.com/map-widget/` (Яндекс Карты, конструктор «поделиться»),
- `https://www.google.com/maps/embed` (Google Maps),
- `https://www.openstreetmap.org/export/embed.html` (OpenStreetMap).

Тему или модуль, которому нужна карта, строят на `<iframe src="https://yandex.ru/map-widget/v1/?...">`. Другой адрес браузер заблокирует. Политика одинакова в `core/security-headers.php`, `.htaccess` и `nginx.vhost.example` (это проверяет тест), потому что страницы из кэша отдаёт веб-сервер без PHP. Чтобы разрешить ещё что-то, правится строка во всех трёх файлах.

## Счётчики и подтверждение сайта (Метрика, Вебмастер, Директ)

В админке «Настройки» есть раздел «Аналитика и вебмастер»; то же делает агент через `set_settings` (ключи `yandex_metrika_id`, `yandex_metrika_options`, `yandex_webmaster`, `verification_tags`; значения проверяются, пустая строка выключает). Это настройки сайта с историей ревизий, как название сайта.

- **Яндекс Метрика.** Нужен только номер счётчика. Ядро пишет в `<head>` тег `<script src="/assets/analytics.js" defer data-ym="..." data-ym-options="...">`, а файл `assets/analytics.js` сам подключает `https://mc.yandex.ru/metrika/tag.js` и вызывает `ym(номер, 'init', ...)`. Inline-скрипта нет, поэтому политика безопасности остаётся строгой. Параметры: `webvisor`, `clickmap`, `trackLinks`, `accurateTrackBounce`, `trackHash`.
- **Счётчик получают только страницы, которые видят поисковики.** Личный кабинет, поиск, ошибки и любые страницы с `noindex` счётчик не загружают, поэтому персональные данные не попадают в Вебвизор. Подтверждающие метатеги ставятся на все страницы.
- **Яндекс Вебмастер.** Поле принимает только код (то, что в `content="..."` метатега `yandex-verification`).
- **Директ, Google, Bing и всё, что просит подтвердить сайт метатегом.** Поле «Другие метатеги подтверждения»: по строке `имя=значение`, не больше 10 строк. Названия, меняющие поведение страницы (`robots`, `viewport`, `refresh`, `content-security-policy` и подобные), не принимаются. Сам Директ кода на сайте не требует: цели и аудитории он берёт из счётчика Метрики.
- **Политика безопасности.** Для счётчика в `script-src` добавлен `https://mc.yandex.ru`, в `connect-src` `https://mc.yandex.ru`, `https://mc.yandex.com`, `wss://mc.yandex.ru` (Вебвизор), в `frame-src` `https://mc.yandex.ru`, в `worker-src` `'self' blob:`. Строка одинакова в `core/security-headers.php`, `.htaccess` и `nginx.vhost.example`, её сверяют тесты. Других сторонних скриптов она не пускает.


## Перенос сайта с другой CMS: функции ядра для модуля импорта

Модуль, который переносит сайт с WordPress, Tilda, Bitrix и других CMS, пишет только через функции ядра: так каждое изменение проходит проверку схемы, попадает в историю и откатывается. Все функции берут `Actor`: на странице модуля в админке это `$actor` из `handleAdmin(ModuleRequest $request, Actor $actor)` (человек с его сессией), в консоли `Actor::cli('import')->withSession('import-' . date('YmdHis'))`.

| Функция | Что делает |
| --- | --- |
| `Content::createPage(Actor $actor, string $slug, array $fields): array` | Новая страница. `fields` как у инструмента `create_page`: `title`, `parent_slug`, `meta_title`, `meta_description`, `og_image`, `is_published`, `sort_order`, `published_at` (`ГГГГ-ММ-ДД` или `ГГГГ-ММ-ДДTЧЧ:ММ:СС`), `schema_type` (`Article` для записи), `blocks`. Родитель создаётся раньше детей. |
| `Content::updatePage(Actor $actor, string $slug, array $fields): array` | Правка метаполей или замена списка блоков (например, после переноса картинок и ссылок). |
| `Content::addRedirects(Actor $actor, array $items): array` | 301 со старых адресов: `[['from' => '/2019/05/post/?p=12', 'to' => '/blog/post'], ...]`, до 1000 за вызов (`Redirects::MAX_BATCH`). `from` нормализуется (без хоста, без хвостового `/`, процентная кодировка раскрыта, кириллица допустима, метки `utm_` и порядок параметров не важны). `to`: путь существующей страницы или https-адрес другого сайта. Адрес страницы, системный адрес и адрес модуля заняты; цепочек и петель не бывает (цель всегда страница). Одна ошибка отклоняет весь список (`ValidationException` со списком). Повторный вызов с теми же данными ничего не меняет. Ответ: `added`, `updated`, `unchanged`. |
| `Content::removeRedirects(Actor $actor, array $fromList): array` | Удаляет редиректы по исходным адресам. Ответ: `removed`, `missing`. |
| `Content::setMenu(Actor $actor, string $name, array $items): array` | Меню `header` или `footer`: `[['title' => '...', 'url' => '/...'], ...]`, до 30 пунктов. |
| `Media::importFile(string $path, int $quality = 82): string` | Картинка из локального файла (выгрузка, распакованная на сервере): те же проверки, что у загрузки (до 10 МБ, JPEG, PNG, GIF, WebP), сжатие в WebP. Возвращает `/assets/uploads/<хэш>.webp`, исходный файл не трогает. |
| `Media::importUrl(string $url, int $quality = 82): string` | Картинка по адресу, `https` или `http`, до трёх переадресаций. Адреса внутренней сети отклоняются на каждом шаге. |
| `RichText::sanitize(string $html): string` | Очистка HTML для поля `richtext` (белый список описан в `docs/THEMES.md`). `SchemaValidator` вызывает её сам, модулю она нужна, чтобы заранее посчитать длину или заменить адреса картинок в уже чистом HTML. `RichText::href()` и `RichText::src()` говорят, годится ли адрес для ссылки и картинки. |
| `CircuitBreaker::allowBulkCreate(Actor $actor, int $count, string $reason): array` | Поднимает лимит новых страниц для сессии этого человека: ещё `$count`, всего не больше 5000 (`CircuitBreaker::BULK_MAX`) вместо обычных 500. Только `system.manage` и только не токен агента (агентам лимит не меняется), у `Actor` должна быть сессия. Пишется в историю «Система» с причиной, действует, пока живёт сессия предохранителя (до суток). В такой сессии правка страниц, созданных ею же, не считается в 15% изменённых страниц: импорт может создать страницы, а потом поправить ссылки между ними. Страницы, которые были до импорта, охраняются как обычно. Ответ: `session`, `limit`, `created`. |
| `CircuitBreaker::claimSession(Actor $actor, string $session): void` | Закрепляет рабочую сессию долгого задания (импорт `imp-<номер>`, который пишется порциями в следующих запросах и фоновом тике) за тем, кто его начал: агент по его токену (`tok-<id>`, независимо от часа), человек по имени. Первый владелец остаётся: сессию чужого токена или сессию, в истории которой уже есть правки другого, не закрепить (`ForbiddenException`). Нужно `content.write`. Вызывайте в момент запуска, с `$actor` запроса, а не с производным `Actor` задания. |
| `CircuitBreaker::ownsSession(Actor $actor, string $session): bool` | Своя ли это сессия: часовая сессия того же токена (`tok-<id>-...`) или закреплённая им через `claimSession`. Токен с тем же именем, но другим номером, чужой. |
| `CircuitBreaker::allowRollback(Actor $actor, string $session, string $reason): array` | Открывает явную отмену сессии (ниже). Разрешено человеку (и консоли) с `system.manage`; агенту только для сессии его же токена (`ownsSession`), для сессии человека или другого токена `ForbiddenException`. Пишется в историю «Система» с причиной и в журнал (`circuit_breaker.rollback_allowed`), действует неделю (`CircuitBreaker::ROLLBACK_TTL`), повторный вызов продлевает. Ответ: `session`, `pages` (сколько созданных ею страниц ещё на сайте), `until`. |
| `Content::rollbackSession(Actor $actor, string $session, array $slugs): array` | Переносит в корзину страницы из `$slugs`, созданные сессией `$session`, **не считая их в 15% предохранителя**: этих страниц до сессии не было, их удаление не трогает того, что было. Работает и через сутки, и через неделю после импорта, когда сессия предохранителя давно забыта; в суточном окне агента эти удаления тоже не считаются. Нужен `allowRollback` для этой сессии, а `$actor` это тот, кто его вызвал, или актёр внутри самой сессии (задание модуля, которое продолжает работу в следующих запросах). Страница остаётся (`kept` с причиной), если её создала не эта сессия (последнее создание по адресу), если после создания её меняли вне этой сессии (правка, удаление и восстановление, перенос на этот адрес), если у неё есть дочерние или это главная. Дети удаляются раньше родителей. Каждое удаление обычная ревизия «Удаление страницы» в истории, страницу возвращает `restorePage`. Заморозка записи действует как обычно (`FrozenException`). Ответ: `deleted`, `missing` (страницы уже нет), `kept` (адрес => почему). |
| `Slug::fromTitle(string $title, int $max = 60): string`, `Slug::free(string $title, string $prefix = ''): string` | Адрес из заголовка (кириллица транслитерируется); `free` подбирает свободный, с `-2`, `-3`, и не берёт адреса удалённых страниц и модулей. |

**Отмена большого импорта.** Без явного пути удаление созданных страниц считается правками: через сутки сессия предохранителя `imp-<номер>` забыта, и отмена импорта в 300 страниц на сайте из 100 упирается в 15%, а агенту массовое удаление закрыто совсем. Порядок: при запуске переноса `claimSession($actorЗапроса, 'imp-5')`; при отмене `allowRollback($actorЗапроса, 'imp-5', 'Отмена импорта ...')` (человек с `system.manage` или тот же токен агента), затем порциями `Content::rollbackSession($actorЗадания, 'imp-5', $slugsЗадания)`. На старом ядре без этих функций (`method_exists`) модуль остаётся при обычных лимитах.

Чего ждать от ядра:

- Одна и та же картинка (по SHA-256 исходных байтов) сохраняется один раз: `importFile`, `importUrl` и загрузка в админке вернут путь, сохранённый в первый раз, пока файл лежит в медиатеке.
- Повторы сохранения страницы безопасны: если документ не изменился, ревизия не пишется (`changed: false`).
- Переименование страницы (`renamePage`) тянет за собой редиректы, которые на неё указывали: цепочка не образуется.
- Новая страница по адресу, с которого был редирект, занимает адрес, редирект исчезает.
- Тег кэша `children:<родитель>` сбрасывается при изменении дочерних страниц: блок `child_pages` и свои списки через `ag_child_pages()` обновляются сами.
- Исключения: `ValidationException` (данные не прошли проверку, `getMessage()` перечисляет ошибки), `NotFoundException`, `ForbiddenException`, `FrozenException` (запись заморожена), `CircuitBreakerException` (сработал предохранитель: остановитесь и сообщите человеку).
